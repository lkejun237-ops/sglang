## 保留的超时策略与根因

直接 WebSocket 的输入队列仍为一条消息，客户端接收队列也保持有界。
source ACK 与 RGB 输出共用写锁；慢消费使写出等待，也会推迟服务端读取
新的 source 消息。接收队列饱和时，协议读取暂停，排在数据之后的 ping/pong
不能及时处理。因此，应用仍在工作或仍发送 heartbeat，不保证 WebSocket
心跳能在原 20 秒期限内完成。

本次保留既有的有限心跳策略：这种慢消费者可以触发超时取消，不承诺完整
输出。没有提高心跳超时、增大队列、降低原 4 秒消费延迟或替换业务负载。
如产品需要承诺更慢的消费者仍能完整输出，应另外设计有界的应用输出 credit
与控制通道；本修复不声称已解决该产品能力。

历史 GPU 记录在 39 帧后失败，harness 随即停服，所以原
`scheduler_released=false` 不能证明持续运行服务永久泄漏。
CPU 双向组件复现保留原 4 秒延迟和默认心跳：约 40.13 秒发送
`1011 / keepalive ping timeout`，保持服务运行后下一连接可用。
组件输入为合成控制消息，不是业务基线；真实业务另行验收。

## 清理修改

这里复用 LingBot World、MinWM 与 Zing 共用的 API / worker 会话清理，
只补充重复取消保护和 Zing 已释放状态的统计修正。#274 的 disaggregation
重构收敛 Encoder 控制恢复，但其冻结版本仍保留 producer 排空和原等待
上限，不能替代本次 API 清理保护。分层与组合验收边界见代码目录中的
[STREAMING_DESIGN.md](../../python/sglang/multimodal_gen/runtime/pipelines_core/stages/model_specific_stages/zing_h3/STREAMING_DESIGN.md#清理层次与框架复用)。

- 连接处理任务取消后，由独立任务完成 watchdog / 初始化任务停止、在途
  GPU RPC 排空、输出取消、scheduler 释放、输入文件清理和 admission / gateway
  lease 归还。再次取消处理任务不会中断这一顺序；完成后再传播取消。
- scheduler 释放与普通 socket 心跳分开。原每次 2 秒等待可能丢弃仍在进行的
  Encoder 清理 ACK。其默认 producer RPC 为 120 秒，现有 dispose 允许
  `6 * 120 + 2 = 722` 秒排空；释放重试共享有限 900 秒总预算。
  正常 ACK 到达即返回，不固定等待 900 秒。scheduler 失联时，取消中的
  admission 可能继续占用至此预算到期；外部强制结束进程仍会中断排空。
- 成功 dispose 后，Encoder 的预取历史水位不再计为保留输入。原水位保留用于
  历史统计，但资源计数归零；只有 producer 已退出、队列排空后才进入 disposed
  状态。首轮真实慢消费日志中的约 2.4 MB 残留值来自旧水位计算，控制回归
  覆盖预取领先 dispatch 时的 dispose。
- 既有清理失败日志仍报告未确认释放；永久不可达的 worker 或 CUDA/driver
  故障需要运维处理，本次不声称自动恢复。错误内容、代码和 close reason
  没有改变，英文契约保持原样。

## 验收

CPU 回归区分控制层与模型能力：延迟 2.1 秒的释放 ACK 在旧 2 秒等待下失败；
修复后一次请求成功。多次处理任务取消，包括 lease 归还期间的取消，均等待
清理完成。真实 Uvicorn `websockets` 后端的有界背压回归覆盖超时、会话退出与
下一连接可用；该快速回归缩放组件时钟，不能替代原默认时钟复现或 GPU 业务验收。

最新冻结源码的云端 CPU 回归：143 项通过（作业 `dlcm40jrft8z172s`）。
本地对应 CI 控制回归：82 项通过，GitHub CI 通过。
首轮 GPU 作业 `dlc1mqbxfvamo308` 完成所有会话与释放检查，但资源计数
归零检查发现上述水位问题，因此不计为完整验收通过。
修正后的 GPU 作业 `dlcrnttzfnk2amkg` 已完成，零 GPU 后处理作业
`dlcsrs7ijc439zab` 核验了 16 个会话的缓存计数归零、scheduler 释放和输入
文件移除。每次清理均在服务持续运行时观察；Encoder ping 显示空闲且无需
重启，输出共享内存文件为零。

| 用例 | 结果 | 清理耗时 |
| --- | --- | --- |
| 服务启动后首个 4 秒慢消费者 | 51 帧后 keepalive timeout | 0.178 秒 |
| 三轮预热后 4 秒慢消费者 | 均在 192 帧后 keepalive timeout | 0.321–0.812 秒 |
| 25 秒请求超时 | 取消，收到 26 帧 | 0.566 秒 |
| 在途主动断连 / 结束时断连竞态 | 取消，随后 17 帧诊断会话成功 | 2.584 / 2.547 秒 |
| 正常及取消后的完整会话 | 7 次全部完成 720 帧 | 0.062–0.074 秒 |

清理耗时来自服务端 cleanup start / done；客户端进程耗时还包括消费等待
和关闭握手，不能作为配置超时期限。7 次完整 RGB 输出 SHA256 一致：
`e68bda6a0071fc7c34448c3a01cc9f74a440e4c9999da11e85cd489f6506417d`。
source 待处理峰值 68 帧，Encoder 完成队列峰值 2，输出结果队列峰值 1。

显存经预热后稳定为 DiT 132,762 MiB、Encoder 10,130 MiB；7 个常驻
进程、300 个线程保持稳定。但主机 RSS 总和从约 13.48 GiB 增至 13.74 GiB，
其中 DiT worker 增长约 215 MiB。**默认启动环境的主机资源验收未通过**：资源计数和输出
哈希通过不代表 RSS 增长已排除。私有 heap 诊断副本与生产源码验收分开报告：
带 GC / tracemalloc 的诊断没有发现残留 source session，pinned 分配量稳定，
但明显改变了运行时序，因此另用只读堆统计复查。

原启动环境的只读统计作业 `dlc1nuzl6zxibjlw` 完成六轮慢消费与下一完整会话，
共 14 个会话，8 次完整输出哈希仍一致。DiT 存活堆仅在约 2239–2245 MiB
之间波动，pinned 分配量保持不变；RSS 从约 7512 增至 7840 MiB，glibc
空闲堆从约 144 增至 461 MiB。增长主要表现为分配器保留的空闲页，但这仍
不满足 RSS 稳定要求，不能将逻辑资源计数归零当作主机资源通过。

追加启动配置 `MALLOC_ARENA_MAX=2` 已在同一 Linux/glibc 环境完成核验
（GPU 作业 `dlc18lx5or3az6ac`、零 GPU 复核 `dlc19fvxu3saznav`）。该变量在启动 Python 与子进程前设置，未修改
通用服务默认分配器；只读统计同时确认实际 arena 数。其作用见
[glibc 官方文档](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)。
14 个会话均确认释放，六轮慢消费者均收到 192 帧后超时取消，清理耗时
0.320–0.813 秒；8 次完整 720 帧输出哈希与主验收一致。实际 arena 数始终
为 2，DiT RSS 在约 7501–7601 MiB 内波动，基线 7557、最终 7599 MiB；
后段五次记录在约 7576–7601 MiB 内，未复现默认环境的逐轮增长。
存活堆约 2239–2245 MiB，pinned 分配量在首轮预热后不变，7 个进程、
300 个线程稳定。DiT 显存通常 132,762 MiB（一次采样 132,808），Encoder
10,130 MiB。预热后完整会话的客户端测量为 41.11–42.16 秒，默认环境
对照为 40.99–42.80 秒；冷启动分别约 120.13 / 121.00 秒。

因此本机型与固定负载的重复取消资源验收，以启动前设置
`export MALLOC_ARENA_MAX=2` 为条件通过。该配置须覆盖 API、scheduler 和
GPU worker 子进程，不能仅在客户端设置。证据来自只读统计副本，没有
GC、tracemalloc 或主动释放堆页干预；未改变模型、队列或心跳配置。
这不是任意运行时长、其他系统或负载下的内存保证，也不能把默认启动环境
标为通过。#250 生产启用前须采用并复核该启动条件；若要求 4 秒慢消费者
仍完整输出 720 帧，现有心跳策略仍是独立阻塞项。

真实 GPU 使用同一服务串行执行正常 720 帧、三次每输出 batch 延迟 4 秒的
原慢消费、请求超时取消和主动断连；每个慢消费或超时取消后都运行下一完整
720 帧会话。主动断连的短会话仅作为在途 RPC 取消诊断。
输入为默认真实 source + 六张参考图，四步、音频关闭、window=6/sink=3、
`[3,2] / split_first_latent=true`，与 R8 原慢消费配置一致。
请求 SHA256 为 `eca7de9535acd0a5822426201cda0dc37defa3affa4e8a1e4244bae5fdf4fdf5`。
source 与六图重新核验 SHA256；66 个模型文件的路径、大小、mtime 绑定既有
完整哈希回执，本轮没有重新对全部权重做内容哈希。
两卡实测均为 274,113 MiB、compute capability 10.3（驱动报告 NVIDIA L20D）。
这不是默认 21/3 窗口、音视频、原生 Zing parity 或持续 24 FPS 的验收。
