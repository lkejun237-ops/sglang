title: "Adaptive source selection in Whitebox"
description: "Feed a model segment without an added sampling timer; prefer even capture spacing only when input is sufficient."
---

The current implementation uses native source demand to distinguish input
shortage from pipeline work in progress. Standalone Encoder–DiT–Decoder groups
and the integrated entry point share progressive input/output contracts. The
candidate is based on `main@4229aa4df5`; GPU and browser results must be recorded
for the actual deployed revision, not inferred from CPU tests.

Historical baseline: the previous cadence/PI implementation was deployed to the
Shanghai copy at `412589f5` with SDK `4c10ad26`. Its 190-second server session
proved generation and release, not browser acceptance or absence of performance
and image-quality regression. Historical results below retain that boundary.

## Scope and configuration

Use `WHITEBOX_MODEL_SOURCE_SAMPLING=adaptive` on a Room with
`WHITEBOX_RENDER_SEGMENTS=1`. The default is `latest`, including historical
bundles without the new variable. Non-segmented legacy paths keep their existing
latest-frame behavior. Enabling the policy does not change CLI FPS, model FPS,
model weights, resolution, encoding, the SDK world clock or Slot ownership.

For a future reviewed release, the existing policy compiler accepts this overlay:

```json
{
  "media": {"cli_fps": 60},
  "environment": {
    "room": {"WHITEBOX_MODEL_SOURCE_SAMPLING": "adaptive"}
  }
}
```

60 FPS is a requested capture ceiling. The source may deliver fewer real frames.
No live configuration or default capture rate is changed by this implementation.
Publication still requires the complete frozen release bundle and normal release
procedure; setting one environment variable does not bypass bundle validation.

## Selection policy

The source owner already retains a byte-bounded `SourceFrames` history for start
boundaries and Prefill. Each model segment borrows at most its eight newest
entries for one synchronous decision. The sampler keeps no RGB pool or task.
Source preview and complete-source recording continue independently.

The existing pair, encoder-credit and output-window gates remain authoritative.
After they permit a source send, the selector follows these rules:

1. Preserve the exact pinned F0 and the first capture satisfying a trusted context
   boundary. During initial output warmup, use the ordinary latest capture.
2. Prefer latest during a pending condition change or changed input evidence.
   A persistent observed-input receipt is not a new control on every capture.
   Unverified effective input still requires the latest pixels, but does not
   bypass cadence admission indefinitely. Input messages and Prompt controls
   continue on their existing independent path.
3. Supply the native next-group dependency before ordinary cadence admission.
   A model can need input even while its total in-flight count is high. The
   negotiated first-output minimum remains a separate safety floor. Existing
   usable history may refill that floor only within the same input/context
   identity and freshness bounds.
4. With sufficient outstanding input and a healthy cadence estimate, defer an
   ordinary capture whose timestamp precedes the next sampling opportunity.
   Wait for a real capture, model progress or source stop, outside the source-send
   lock. A new control may advance one opportunity; later updates coalesce until
   that opportunity instead of creating an unlimited burst. Initial output,
   condition boundaries, EOS and an input window below its floor bypass this gate.
5. For an admitted capture, prefer a capture closest to the next
   expected capture time. Candidate versions must exceed the consumed selection
   cursor, have matching input evidence, and be no more than 100 ms old both in
   Room observation time and relative to the newest capture timestamp. Ties
   favor freshness. Large phase errors re-anchor to latest.
6. With no eligible older candidate, select the admitted latest capture. After
   prolonged backpressure, re-anchor to current capture time instead of catching
   up missed opportunities in a burst. Never duplicate or predict a source frame.

The minimum-input floor is the existing negotiated/profile-dependent pipeline
requirement, not a newly assumed batch size. `sent - received` counts work not yet
returned as model output; encoder consumption alone can release source storage
before that work finishes and is not a reliable measure of available model work.

## Native flow and cadence estimation

`source_flow` declares the clip17 encoder groups (`1/8/8`), the source dependency
of the actual first AR block, and progressive output support. The current unsplit
`[3,2]` plan needs nine real source frames for its first output. This minimum is
not an inventory target or a batch that Room must collect before sending.
Independent Decoder open replies propagate the actual release/output capabilities
through DiT and Encoder. Room requires the valid-source release contract before
using the negotiated minimum; old peers retain their legacy capacity checks.

Room requests `source_demand_protocol="source-demand-v1"`. A capable input owner
reports `source.demand` with session/generation identity, a strictly increasing
sequence, accepted and dispatched source ends, the next required source end,
queued source frames, whether it is actually waiting for source, and cumulative
source-wait milliseconds. A future dependency reported during compute is distinct
from an idle input wait. These observations do not release memory credit:
`source.consumed` still means ownership transfer, not GPU completion.

Streaming demand is suppressed until startup preparation/attachment finishes, so
it cannot displace an ordered startup reply. Condition, pause and EOS controls
keep their own ordering. Native input waits wake for complete encoder dependencies
or controls rather than dispatching an incomplete group on a fixed collection
timeout. Existing clients that do not opt into demand receive no new event type.

Demand publication must not block the next compute dispatch behind RGB output.
Each generation owns one sender and one replaceable pending observation, never
a queue of old snapshots. The sender takes the transport lock before reading the
current published-input state and allocating its sequence; input-wait accounting
is updated at the actual scheduling boundaries independently of send delay.
Failure cancels and joins the generation and publisher; successful completion or
cancellation discards unsent advisory state, with no messages in the next session.
Hard source credit and output ownership are unchanged.

The output writer waits for decoder materialization and builds the payload before
acquiring the transport lock. A split frame header and its binary pixels remain
one atomic send group; control messages may pass between complete frame batches,
but never between a header and its pixels. The existing bounded output task keeps
chunk and condition order, including cancellation of unconsumed async references.

Each segment starts with bounded latest supply to observe attainable pipeline
cadence independently of a soft admission gate. A probe spans at least two
seconds after its first output anchor. Capture version/PTS progress must show
source headroom; a source-limited run does not lower the model estimate. The
probe preserves the same frame/byte/age limits as normal operation.

Steady observations span at least one second. Own admission deferrals and native
source waits invalidate downward learning. Healthy supplied observations retain
an 80/20 EWMA; a faster observed completion rate can improve the estimate even
while demand recovery is active. Two rejected windows more than 10% slower than
the estimate, with source headroom, trigger another bounded-latest probe. This
permits real slowdowns and recovery without locking the fastest rate forever or
resetting Prompt/cache every five seconds. Pause, condition barriers and EOS are
excluded from normal learning. Native observation windows exceeding four seconds
are abandoned rather than interpreted as normal throughput.

The small queue correction is proportional only: no integral or derivative. Its
target is one maximum native encoder group (eight frames for this contract), not
the first-output minimum and not `sent-received`. It uses reported unprocessed
source plus newly submitted input, is disabled without fresh demand, and can
increase the measured period by at most 5%. Input shortage removes the correction.
Total unfinished-frame age remains a diagnostic, not evidence of queued input.

Older workers without negotiated demand use bounded latest supply and report
`effective_mode="latest_unverified_supply"`. A measured segment reports `adaptive`
or `adaptive_probe`. The original source timestamp, pixels, UI/input identity and
native indexed model clock remain distinct and unchanged. There is no fixed
24-FPS cap, frame duplication or global state shared between players.

## Interaction, cancellation and limits

Keyboard input continues through the existing immediate input path. An eligible
Prompt update can reach the worker while no new capture is arriving; a request
that explicitly targets a future source/context boundary still waits for that
boundary under the original protocol. The sampler never changes its meaning to
make a control request appear faster.

Source stop/cancel retains the existing fence. EOS follows the existing latest
tail behavior rather than replaying a backlog of historical captures. Parent Slot,
child segment and shared CLI cleanup responsibilities do not change.

There is no new playout queue, sleep, future-frame timer or change to RTP pacing.
Cadence admission waits on capture/progress notifications and can change when
model input is submitted; it is not a guarantee of unchanged model-visible latency.
Choosing an older eligible capture can nevertheless add up to the configured
100 ms freshness bound to source age. Control guards prefer latest, but a CPU
contract test is not proof of unchanged visible input latency. In particular,
unknown effective input after interaction conservatively stays on latest.

Uniformity is best-effort. With only one available candidate, or where source
timestamp quantization already determines the minimum variance, the result may
be identical to latest. The implementation cannot create missing source frames,
remove network congestion or guarantee a real model/render FPS.

## Diagnostics and verification

Model recording manifests gain `source_sampling` only when adaptive selection is
active. It contains decision counts, reset and rate-observation counts, estimated
completion period, maximum extra capture age and admission counts for early
captures and control advances. It also exposes effective mode, native demand
watermarks and wait totals, rejected capacity samples/probes, and bounded-P queue
correction. A capture-slow probe or fallback is not claimed as active regulation. Decisions are not accepted-frame
counts or a substitute for actual input/output counters.

The 2026-11-10 focused CPU suite covers 40 cases, including deferred-input
control dispatch, progress/EOS wakeups, non-consuming pinned-F0 notifications,
cancellation and 36 FPS capture against batched 18.6 FPS virtual model demand.
In those virtual schedules, P95 selected-capture gaps fall from 250–472 ms to
56–83 ms with unchanged steady consumer throughput. These are simulated capture
intervals, not measured GPU output, browser presentation or user input latency.

CPU tests cover fluctuating source rates, healthy completion windows versus source
starvation, duplicate/batched observations, no-candidate waits, low-water tail
feeding, pinned/context boundaries, input and Prompt dispatch, EOS/cancel and
player isolation. A deterministic virtual schedule compares latest and adaptive
selection at identical consumer opportunities; both retain the same number of
unique samples. It is not a model or browser FPS benchmark.

The 2026-11-05 local regression run completed with 301 passed and 10 skipped.
The skipped immediate-capture codec cases require the native x264 bridge, which
is unavailable in the local test environment. Existing WebSocket dependency
deprecation warnings do not concern this sampling policy. The run also covered
source conditions, Prefill/startup, player lifecycle and independent/streaming
recording, beyond the focused command below.

```bash
PYTHONPATH=python SGLANG_LIGHTWEIGHT_RUNTIME=1 python -m pytest \
  python/sglang/multimodal_gen/test/unit/realtime/test_whitebox_source_sampling.py \
  python/sglang/multimodal_gen/test/unit/realtime/test_whitebox_render_lifecycle.py \
  deploy/whitebox/test_release.py \
  --confcutdir=python/sglang/multimodal_gen/test/unit/realtime -q
```

Before enabling a production release, compare latest/adaptive with the same
world, actions, weights, source rates and hardware at 480 and 736 output sizes.
Measure unique input/output/display FPS, capture spacing and age, input-to-visible
latency, Prompt-to-first-new-condition frame, freezes, queue age, and
Encoder/DiT/Decoder time and memory. Include source slowdowns and recovery,
Prefill/segment changes and active controls. The isolated 480 server-side results and observed costs are recorded below.
736, browser/multiplayer acceptance and component peak-memory measurements remain
unmeasured; neither the virtual schedule nor past deployments proves them.


## Input renewal hints and historical PI

Known held-key/button renewals still reach the SDK with every original sequence
and receipt. They do not create a new sampling priority revision. Edges, pointer
events, unknown envelopes, effective-input and context changes remain freshness
signals; observed receipts are not proof that an input is already visible.

The 2026-11-10 implementation used a PI correction on total in-flight frames,
with a target derived from the minimum input floor and a scale up to 1.15. The
current implementation replaces that feedback with native source demand and a
small queue-only P correction. A bounded multiplier did not bound overall
slowdown when completion-rate estimation also learned the input wait introduced
by the controller itself. Historical virtual/production measurements of that PI
are not acceptance evidence for the replacement.

The native regression suite includes fixed-cost three-stage pipelines, genuine
capacity changes, slow/absent supply, generation fences, independent controls,
progressive publication before later latents finish, and source ownership/EOS
checks. It does not estimate real GPU gains. Run matched latest/adaptive trials
on the actual 480 and 736 deployments before making throughput, latency, memory
or quality claims. Browser acceptance remains separate from server generation.


## Isolated validation, 2026-11-12

Three 190-second real CLI/model sessions at 832×480 and CLI36 exercised the same
H100 Encoder/Decoder and H200 SP2 group. Native demand and the progressive release
handshake were observed, with successful release and subsequent sessions. Whole-
window model FPS was26.295 (first adaptive),27.247 (latest),26.126 (warm adaptive).
The warm adaptive repeat was4.1% slower and had higher source-to-raw/input P95;
this is not an unconditional speed or latency gain. Both modes showed previously
observed long-session quality deterioration. See the
[validation report](../../../../../benchmark/whitebox/unified_progressive_validation_20261112.md)
for startup effects, missing input samples, source/image identities and untested
736/browser/cache/multiplayer boundaries. Production was not changed.
