## Whitebox 主线整合与 KV 配置迁移（2026-11-08，候选待验证）

本轮将 `main@4e20c16008`（私有捕获 stream、边界图策略与共享 KV 预算）合入
`white_box@af9ea3bf31`，保留同条件 GPU Prefix 复用、运维定时刷新、受管 Prefill
和玩家生命周期接口。这是11月8日的历史整合记录；11月9日起正式发布使用远端 `main` 的完整 SHA 与固定 SDK，不从white_box部署。

新版拒绝 `zing_kv_pool_size/max_target_area/max_target_long_edge/max_prefix_rows`
四项旧容量字段。部署须移除这些字段，按显存预算提供 `mem_fraction_static`；不能
把旧 JSON 原样用于新 runtime。每 Worker 单玩家、区域 source/target 分辨率、精度、
Sink 策略及 L1/L2 预算仍按已冻结配置明确传入，不以合并变更自动扩容。

本候选尚未完成 CPU 集成、GPU 或线上验收。主线历史 480/H100 结果不证明
泰国 480 输入/736 输出、B300、FP8 的新组合通过；合并后的功能、画质和性能分别报告。

## 相同条件刷新与 GPU Prefix 复用（2026-11-06，代码候选，未部署）

基于 `white_box@8b7d81ac86` 整合新 Prefill 后，相同已生效 Prompt 且省略参考图更新时，
原 `prompt.update` 可保留本会话 GPU 静态 Prefix，跳过条件编码与静态 KV 的 CPU→GPU
恢复；最近五个生成 latent 的历史重建仍需计算。条件变化、显式参考图更新及身份不匹配
继续走原路径；SP ranks 一致确认后才复用。该结果标记为 `resident_gpu_prefix`，不是 L1 hit。

Room 运维配置支持 `interval_seconds=0` 关闭、`5` 表示生效后等待约五秒再于安全边界
刷新当前条件；不增加客户端接口、模型 Slot 或共享世界暂停。Prefill、切段、真实条件
更新和退出沿现有串行边界结算。完整配置及生命周期说明见
[Condition 刷新契约](/docs/sglang-diffusion/zing_h3/specs/whitebox-condition-refresh)。

本地 Room/Prefill 集成 258 项通过，缓存/源会话/CPU Graph 模拟及 Encoder–DiT 链路
1013 项通过、18 项跳过；这些不是 CUDA Graph/SP 验收。480/736 的抗漂移画质、FPS、
TTFF/E2E/TPOC/ICL，以及 Encoder（Qwen/reference/source）、DiT、Decoder 的分项耗时
与显存尚未测量；需在获准的真实链路短测中核对，再按需补充同条件性能矩阵。
不能从跳过静态恢复推断整体刷新没有停顿或长期画质已改善。

## 多实例缓存容量修复（2026-11-06，代码候选，未部署）

本次基于 `white_box@f389c2c3b8` 实现同机多实例 L1/L2 容量管理，保持每个 Worker
最多一个活跃 PlayerSession。没有改变模型计算、缓存 key、磁盘格式或客户端接口。

- L1：用同机共享的内核锁记录各 rank 预算；实例额度的 95% 用于分页 KV，5% 留给条件快照。
  正在写盘或 DMA 使用的页不回收；空间暂不可用时跳过可选缓存填充，不阻塞当前推理等待磁盘。
  条目卸载后页在实例内复用。PyTorch 可能保留锁页内存，因此整份实例预算在进程退出后才归还机器。
- L2：同一文件系统共享预算，计入历史目录、临时文件和未完成写入；写前原子预留，后台写入有界。
  多实例可开启 GC，每轮只有一个持锁回收者；活跃读写条目受保护，进程死亡留下的文件仍计费，
  只有实际删除才释放磁盘占用。未登记的历史目录只计量、不自动删除。
- 两地配置模板启用 GC，L2 总预算 700 GB，630 GB 开始回收、目标 560 GB，另保留 128 GB
  文件系统空闲空间；在途写入总预算 128 GB，最多两个不同 key 写入组。以上均为十进制 GB。
  L1 机器总预算保持 416 GB；新增实例必须在此总量内划分额度，不能每个实例各分配 416 GB。
- 模型角色日志轮转为每角色 64 MiB × 4；有界队列持续排空子进程日志，磁盘错误只丢弃诊断。
  这不替代其他应用日志或录像文件的保留策略。

所有实例必须挂载同一份本机容量目录和 L2 根目录。软件预留只约束使用此实现的写入者；
其他训练任务仍可消耗同盘空间，因此运行中每块写入也检查实际余量。配置冲突拒绝启动，
不使用超时抢占活跃进程的预算。GPU 异常保留人工恢复，不自动重启整组模型。
可选的 `deploy/whitebox/instance_capacity.py` 用实测显存 profile 做同 GPU 多实例启动准入，
不是 GPU 调度器，也不会自动提高线上并发。参数与使用边界见
[缓存管理部署契约](/docs/sglang-diffusion/zing/specs/block0-cache-management-api#64-机器容量与多实例启动)。

本次仅完成本地 CPU 契约与真实进程/文件锁测试；CUDA 锁页分配、SP collective、同 GPU 多实例
实测峰值、480/736 的 FPS/输入延迟/画质以及线上端到端均未验收。
5% 条件快照预留会减少 L1 可用 KV 页数；新增文件计量和锁竞争可能影响 L2 读取/恢复时间，
不能引用本页历史 GPU 数据声称本修复无性能退化。

## Whitebox 三玩家录制预算（2026-11-04）

`f8681136b2` 的 Room 录制进程上限为 6，三玩家配置的 9 会在启动时拒绝；
原 96 MiB RGB 总预算也不足以同时保留三玩家各自源流及新旧段的全部 RGB 队列。
本修复将进程硬上限扩为 9，并增加 `WHITEBOX_STREAM_ARCHIVE_RGB_BYTES`，
默认仍为 96 MiB、允许 32–512 MiB。上海三路 832×480 目标配置为 9 进程和
192 MiB RGB 总预算，保留每队列帧数/字节上限、单玩家模型绑定及归档故障隔离。
两路过渡部署继续使用 6 进程和原 96 MiB，不将三路配置强塞给旧镜像。
CPU 检查覆盖三玩家源流与新旧段共 15 个 RGB 队列、总预算耗尽和完整回收；
本修复的真实三路录制、480/736 FPS/输入延迟以及 Encoder/DiT/Decoder
分项性能和显存尚待验收，不能从预算检查推导通过。完整结果记录在本修复 PR。

2026-11-09 上海 PAI OverlayFS：首次 Prefill 前后缓存目录的 `st_ino` 发生变化，
导致 L2 的目录替换保护拒绝读写。StorageBudget 现在持有注册目录的打开句柄，
在预算实例销毁时释放，保持运行期 inode 引用；实际目录替换仍拒绝，禁止自动改写旧登记。
不支持将已失去全部打开引用的旧 OverlayFS 登记当作永久磁盘身份；重启后仍须校验。
这是缓存文件系统兼容修复，不改变模型、容量和采样。CPU 回归与 GPU 复测状态见本次 PR；
GPU 落盘和性能仍待实测，不能引用旧结果作为通过。

独立 DiT 入口同时补齐已有的 `--zing-block0-cache-storage mounted|local`，
默认仍要求真实挂载。PAI 作业使用已核对的本地磁盘时需显式选择 `local`，
部署层在加载权重前创建目录、检查磁盘余量并调用原 `startup_config` 校验；
不会以创建空目录冒充持久挂载。本地 L2 随作业退出可能丢失，迁移前需保全缓存，
不能把旧作业的 OSS 备份说成新服务已召回的 L2。

## 四卡人工发布的 FP8 配置（2026-11-04）

同一发布配置支持 source `832×480`、target `1280×736`：CLI 和传入模型的
source RGB 保持原始尺寸，独立 `model.width/height` 只控制模型输出；Room
按对应尺寸编码、配对和归档，禁止将 source 放大后冒充原生高分辨率输入。
736 配置同时需要扩大 GPU KV pool 的 target area/long edge；不能只修改网页标签。
当前候选 CPU 混合尺寸与真实 H264 契约检查通过，step2000/FP8 的736 GPU性能、
长期画质和浏览器验收尚待本轮发布后验证，历史736数据不作为本轮通过证据。

正式 `deploy/whitebox` 策略可选择 `model.quantization="fp8"` 和
`model.quantization_scope="ffn-attention"`；默认 `none` 及无该字段的历史 bundle
保持 BF16。仅 DiT 追加 `--quantization fp8 --direct-gpu-weight-loading false`，
Encoder/Qwen、Decoder、单玩家容量及原四卡布局不变，KV 不量化。
CPU 回归覆盖参数、scope、配置摘要变化与旧 bundle 兼容。本次新 step002000
模型和量化组合的 480/736 FPS、TTFF、画质及 Encoder/DiT/Decoder 分项耗时和显存
尚待 GPU 验证；不沿用历史 736p 结果，也不将本轮 480p 外推为 736p 已验收。

2026-11-03 动态 Sink 实现基于 `0a4623e129`：缺省 Sink 对齐为两个原生块（unsplit `[3,2]` 下为 5 latent）。显式历史 profile 的 S3 保持原值；启用 `sink.off` / `sink.refresh` 需将 profile 与 KV pool 的启动 Sink 同设为 2（或以 off 启动时同设为 0），并满足 W≥4。仅调整策略与压紧已有 KV，允许在边界单独完成 deferred final，相关停顿和 forward 调用需实测。W6/S2 的 `after_step0` 预分配峰值不因锚点减少而自动下降，不能据此声称解决 736 OOM。冻结运行版本 `d87d75fb16` 已完成 H100 SP2 eager 与 B300 SP1 的 832×480 / 1280×736 功能验证（B300 480 开启 Graph、736 采用 eager）；单次 off/refresh 各多 1 次 deferred-final forward，source/prefix 计算次数不增加。完整产品性能矩阵未测；提 PR 前整合 `main@a9a4b2f93e` 后的首次联合 forward + sink 组合尚未重跑 GPU，CPU 集成回归以 PR checks 为准。源码身份、原始回执、视频及显存口径见 [动态 Sink 验收记录](specs/dynamic-window-sink.validation.zh-CN.md)。

2026-11-03 动态 Sink 实现基于 `0a4623e129`：缺省 Sink 对齐为两个原生块（unsplit `[3,2]` 下为 5 latent）。显式历史 profile 的 S3 保持原值；启用 `sink.off` / `sink.refresh` 需将 profile 与 KV pool 的启动 Sink 同设为 2（或以 off 启动时同设为 0），并满足 W≥4。仅调整策略与压紧已有 KV，允许在边界单独完成 deferred final，相关停顿和 forward 调用需实测。W6/S2 的 `after_step0` 预分配峰值不因锚点减少而自动下降，不能据此声称解决 736 OOM。冻结运行版本 `d87d75fb16` 已完成 H100 SP2 eager 与 B300 SP1 的 832×480 / 1280×736 功能验证（B300 480 开启 Graph、736 采用 eager）；单次 off/refresh 各多 1 次 deferred-final forward，source/prefix 计算次数不增加。完整产品性能矩阵未测；2026-11-06 整合 `main@b9e4bc95fc`（含共享静态 KV 容量、独立服务收尾及 VAE 优化）后的 sink 组合尚未重跑 GPU，CPU 集成回归以本次提交的 PR checks 为准。源码身份、原始回执、视频及显存口径见 [动态 Sink 验收记录](specs/dynamic-window-sink.validation.zh-CN.md)。

## 实例卡顿回归接入（2026-11-07）

默认接入 [serving-stall-v1](/docs/sglang-diffusion/zing/specs/serving-stall-regression)：
832×480／1280×736、四条真实产品 case、冷重启、动态条件、单活跃会话生命周期、
完整 DiT 回放，以及每档三轮、每轮各 rank 至少 600 秒有效完整会话工作的常驻耐久。
复用现有录像时，正常 EOS／释放后开启下一会话，不拼接长上下文。
完整 E1+SP4+D1 测试现在允许显式申请六卡，使用已有碎片主机的六张未分配卡；
旧八卡分配结果仍保留八卡资源成本。该六卡调度组合当前尚未完成 GPU 验证，
不得从原八卡分配直接外推其性能或显存结果。

冻结工具 `55b707eb`／生产 runtime tree `6416ecd5` 的 R69 在 B300 同八卡分配使用
E1+SP4+D1 六张活跃卡；两档 Source VAE 均按生产 resize 编码832×480，736入口／
输出为1280×736。74个普通请求全部成功且完整交付，双档单会话拒绝、断连与恢复通过。
15921帧、24FPS供流、250ms播放缓冲的三轮中，480未检出>250ms播放停顿；736分别
检出1／1／2次，均无>1秒严重停顿。首次换图准备仍需737–924ms，不能宣称736稳定
实时通过或归因reference VAE重编码。480完整DiT三轮数据已采，但预热与native输出
逐位比较失败，严格耐久门禁终止；另立诊断收集双档耐久，不将数值FAIL转成PASS。

候选在ready前collect/freeze静态堆，新会话仍自动GC，退出解冻；捕获时暂缓cyclic GC，
使用进程／设备专有的非池化capture stream。测试EOS复用已有Encoder／Decoder持久
连接。资源清理、listener退出后消费终态输入，profile ACK与close各自独占接收，
避免迟到心跳阻塞有界队列。历史SP2静态GC专项显著降低GC长尾，但整轮耗时仅变化
-0.35%／-0.27%，不能外推稳定吞吐收益；736短请求D2相对D1仍未证明24FPS容量，
不推荐据此改为D2。

上述完整结果使用显式历史S3 profile，未覆盖新主线`526662ade6`的缺省S2或动态sink。
本PR整合该主线后的GPU组合当前未验证；冻结R70耐久、R71同卡`main@b9e4bc95fc`
对照及R74完整DiT补测保持原版本继续执行，不能冒称新缺省验收。完整条件、逐组件
性能／显存、原始数据、失败与未执行项及报告统一回查[PR #580](https://github.com/seedleap/sglang/pull/580)。

R69同一Decoder进程在736三次完整供流会话后，allocated约4.875GiB回落，而reserved
每次增加约5.49GiB，后续诊断结束达264.086GiB。这是allocator缓存高水位线索，不能
直接称为活跃张量泄漏或既有输出停顿的原因。新增候选在原有跨lane step gate下复用
进程／设备私有Decoder CUDA stream，与capture stream分离，保留每会话线程和状态、
输入event等待及取消／quarantine语义。它只针对多stream缓存累积；cuDNN线程缓存等
其他因素仍需检查。480／736同条件前后GPU对照与整体三组件复测当前未完成，
速度和显存收益未验证，不据此修改产品demo。

## Benchmark 留存策略更新（2026-11-05，GPU 性能未重新验证）

新实验默认保留完整指标/输入输出哈希及首个正式请求的有界代表 MP4，结束后在
核实本次 worker 退出、持有专属 owner lease 的条件下清理本次 Block0 磁盘缓存，
实验总留存以 2 GiB 为验收上限。不会改动已运行的任务或共享 Encoder/Decoder 缓存。
原始逐包 RGB 写盘改为哈希/抽帧会影响客户端背压；H100/H200/B300 的 480/736
新模式 E2E、Encoder/DiT/Decoder 耗时和逐 rank 显存均尚未重测，旧数据保留原版本
及保存模式边界，不能归因成模型加速。参数、收尾 API 和验证入口见

## BF16 SP2 的 NCCL 启动配置（2026-11-05）

## 独立服务启动、流控与收尾（2026-11-05）

本组修复独立 Encoder／DiT／Decoder 的启动和会话收尾，不引入共享静态 KV 容量配置。
DiT 在建立 Gloo／NCCL 之前预留服务端口；HTTP／rendezvous 预绑定失败时，leader 保留异常并继续参与内部组初始化，随后与 store 初始化失败共用广播，在模型加载前通知全部 rank 退出。普通 conditioning 拒绝不隔离 worker，模型／CUDA 同步故障仍隔离；早期 init 被拒绝时清理可幂等执行。两个 CPU/Gloo rank 已通过真实 HTTP／rendezvous 端口占用回归；真实多 GPU／NCCL 的启动故障注入仍未验证。

source 与输出尺寸不同时，Decoder 的 `source.consumed` 按原始输入流宽高计算已归还的
RGB 字节，而非输出画幅。仅断开输出 WS 时，Decoder 丢弃迟到的 RGB／credit 并释放
对应引用，仍接收已发送的 NCCL 载荷，直到输入 owner 有序取消；正常输出取消不标记整组故障。
直连 Decoder 的像素绕过输入 WS，故 Encoder 从首个已校验的正帧数 dispatch 回执启动
既有硬时限；继续输入心跳或不发送 playback ACK 均不延长该期限。

释放配对时，Master 先请求 Encoder `quiesce_group`：停止新输入、串行排空已接收工作，
等待 DiT 取消及 Decoder 退出确认，此时保留全部链路；随后并行拆除三个角色的通信组。
正常清理通过幂等重复 `destroy_group` 等到 `disconnected`，不通过空闲状态查询取得新预留。
初始化在首个异步校验前登记到连接，并与输入排空共用 admission 锁；实际 `link.open` 在模型 owner 队列内
重新检查连接状态。排空等待已受理的初始化完成／被拒绝，再等待取消 ACK；不能在 `quiesced` 后新建 owner。
初始化校验失败时允许没有 ledger；普通排空拒绝不标记模型／通信故障。
这是单活跃会话的正确性保障，不改变模型前向、采样或 KV 容量公式；Master 与三角色须共同升级。

**当前合入 main `01ed0ed97a`（含 #517 容量改动）的生命周期组合未进行新的 GPU 验收，也没有本组的速度／显存收益结论。**
历史合并版本 `9b7084342d` 的 H200 两档会话取消、输出断连硬时限和通信组复用数据保留原 SHA，
不能作为这份单独生命周期组合已实测的证明。CPU 回归及历史私有回执入口见
[PR #584 的修复与 CPU 验证](https://github.com/seedleap/sglang/pull/584)，协议见
[连接管理接口](/docs/sglang-diffusion/zing/specs/WORKER_CONNECTION_API)。

## 共享静态 KV 容量与准入（2026-11-05）

通过 `--mem-fraction-static`／`mem_fraction_static` 指定常驻模型与 KV 的静态预算。
两个启动入口均在模型加载前／后清理空闲缓存并测量实际可用字节，再按实际层数、局部 heads、
head_dim 与 dtype 换算一个共享 slot 的总行数，逐 rank 取最小值；prefix、source、target 共用容量。
保留至少 8 GiB 运行时空间，并分别检查分片联合 forward 与每 rank 完整 7,168 维 prefix 的工作区。
具体公式与输入策略见[容量契约](/docs/sglang-diffusion/zing/specs/PERFORMANCE_DEFAULTS#预分配-kv-池的容量字段)。

## Block0 Mooncake 后端候选（默认关闭）

2026-11-09 的 `white_box` / `main` 合并保留 local 共享容量、L2 写前预留与 GC 保护，
Mooncake 继续使用独立共享内存后端；启动配置、Prefill 回执和恢复监控按后端区分。
local 页数统计不套用到 Mooncake，无 CUDA 恢复事件时不填 GPU 计时。
本次组合只进行 CPU 合约回归，未部署；480/736 的同条件 E2E、Encoder/DiT/Decoder
延迟、常驻/峰值显存及画质仍未验证，不能沿用下方历史实验数字宣称无退化。

**本 PR 只提供可选后端，业务适配与上线启用尚未确认。** 默认
`--zing-block0-cache-backend local`，保留原版 pinned 页池、磁盘 L2、文件索引和既有配置。
安装 Mooncake 或提供客户端 JSON 均不会自动切换后端；现有部署不修改。
业务行为差异和待确认清单见[缓存管理契约](/docs/sglang-diffusion/zing/specs/block0-cache-management-api#业务接入待确认项)。

在已启用 `--mem-fraction-static` 的有效运行配方上，实验部署须显式追加：

```bash
--zing-block0-cache-mode on \
--zing-block0-cache-backend mooncake \
--zing-block0-mooncake-config /path/client.json
```

Mooncake 由独立 Master/Store 管理共享 pinned L1；Worker 只在启动时注册 GPU KV storage，
不创建应用侧 CPU KV 池或 staging。客户端 `global_segment_size=0`，另留默认 64 MiB SDK
元数据工作区（`metadata_buffer_bytes`，正整数），只传 conditions、manifest 和索引。
真实 conditions 超出工作区时写入会失败，不会自动扩容；当前真实大 conditions 尚未验收。

```json
{
  "master_server_address": "master:50051",
  "master_http_url": "http://master:9003",
  "metadata_server": "P2PHANDSHAKE",
  "metadata_buffer_bytes": 67108864,
  "protocol": "tcp",
  "namespace": "zing_b0"
}
```

`master_http_url` 指向 Master 管理端口（`--metrics_port`），不是 TransferEngine 的
`http_metadata_server_port`。Master 使用 `--enable_offload=false`，Store 禁用 SSD offload，
不配置持久化路径。Store 的 `global_segment_size` 为共享池预算，`local_buffer_size` 可为 0。
设置 `MC_STORE_PIN_MEMORY_MAX_BYTES` 至少等于整池预算，并核对 Store 日志 `size=pinned`。
GPU 指针直传要求 Store 可见 CUDA driver/device、memlock 足够；RDMA 还需设备及权限。
客户端和 Store 的 `protocol` 同时改为 rdma，且不能残留 `MC_FORCE_TCP=1`；以实际传输日志为准。

**Mooncake 不使用 L2，不读取/写入/迁移/清理旧磁盘缓存，也没有持久化恢复。**
L2 list/delete/clear 返回 HTTP 501；preload 只检查共享完整性；unload 删除共享条目并影响所有
共享实例，读租约未结束时返回 busy，不强删。Store/Master 丢失或条目淘汰后由业务按需补热。
原生 group 由模型/SP namespace + cache_key 决定，跨全部 rank 的 KV、conditions、manifest
和关联键一致；保留 KV 预检查、manifest 最后发布和发布后整组检查。早绑定索引在本次填充中
暂存并在发布前幂等补回；晚绑定在写完后补查。读端仍逐层核对精确字节数；不新增 pin/unpin。

## 导出时保留训练分块配置

`export_checkpoint.py --config` 应直接使用原始 effective training config，不能为沿用旧部署
而改写 `num_frame_per_block` 或 `split_first_latent`。例如 `[3,2]` 配合 `false` 表示
`3,2,3,2,…`；改成 `true` 会将开头拆成 `1,2,2,3,2,…`，改变模型计算边界。
在 `--provenance` JSON 中提供原始文件的 `original_config_sha256`，导出器会在加载权重、
写出产物前核对输入文件的原始字节摘要，不匹配则拒绝导出；未提供摘要时不校验来源。
验收同时核对导出配置顶层、`training_effective_config` 和实际加载配置，不能只看 `[3,2]`。

该校验不修改已有模型包或线上配置，也不增加运行时对分块组合的支持。恢复
`split_first_latent=false` 前仍须验证目标 runtime 的初始化、prompt/reference 切换和 EOS；
既有 `true` 配置的视频不能当作 `false` 的效果或性能证据。此 PR 未补跑 480/736 GPU，

### 本地 NVMe L2 管理与强制 prefill（PR #467）

2026-10-30 确认先以同机本地 NVMe 为验收和部署范围：各实例独立 L1，同机实例共享一个已挂载的

原子替换，不依赖跨机器 flock，不要求缓存 generation 一致或整组分片原子切换。
各 rank 全部加载校验成功才命中；缺失、读取失败或删除竞争则整组 miss。

### Decoder 拆分（实验布局，未合入默认）

把 Lynn source decoder 放到独立 GPU 进程后，DiT 只收共享内存引用，不再解码也不再
持有像素。2026-10-21/22 在泰国 L20D（CC10.3，274,113 MiB）实测，E1 + SP2、
Qwen 仍在 DiT 进程内、resident AdaLN、W6/sink3、queue2、Graph、720 帧技术负载
（120 帧真实 source 重复六次）、客户端整帧 RGB：

| 布局 | 832×480 稳态 / 全程 FPS | 1280×736 稳态 / 全程 FPS | DiT 每 rank allocated |
| --- | --- | --- | --- |
| E1 + SP2（Lynn 在 DiT 卡） | 20.42 / 19.33 | 8.97 / 8.73 | 178.1 / 197.8 GiB |
| E1 + SP2 + D1 | 25.92 / 23.78 | 11.46 / 10.99 | 172.2 / 188.3 GiB |
| E1 + SP2 + D2 | 26.25 / 24.00 | 11.69 / 11.22 | 172.2 / 188.3 GiB |

D2 相对 D1 只有 +1.3% / +2.0%，落在跨运行方差量级内；收益主要来自把 Lynn 移出
DiT 卡（稳态 +28.5% / +30.4%）。TTFF 增加 0.20–0.33 s，来自 decoder 服务握手。
E1 的 Encoder 走 `unvalidated_group_size` 复制回退，不等同于已验证的 E2 分组。
D1 的下一次 latent 传输不等待前一个 decode job，但共享内存 publisher 容量耗尽时仍有背压。
D2 为避免 tile collective 与 bridge transfer 交叠，下一次 append 在接收 latent 前等待
上一 decode job 完成，因此会阻塞 DiT 的同步发送。该 worker 等待受 `--timeout-seconds`
限制（默认 120 秒），不代表端到端延迟上界；尚未采集 D2 的独立背压耗时。
2026-10-22 在 `e1170da2e3` 上做了三布局 × 两档 × 每次 120 帧、每格两次会话的 smoke：
全部完成，SIGTERM 后 decoder 不残留，decoder 进程落在预期卡上（D1 一张、D2 两张）。
同一布局两次会话逐位一致；但三种布局**彼此不是同一画面**，480p 相对本地解码平均绝对差
2.59–2.74/255（PSNR 33.3–33.9 dB，SSIM 0.941–0.945），720p 为 2.00–2.23
（PSNR 34.1–35.3 dB，SSIM 0.962–0.967），无时间偏移、差异随帧序缓慢增长；
D1 与 D2 之间同样是 2.30/255 量级。差异来源尚未定位，不能把该布局当作与本地解码
逐位等价。未验证：L20X/L20Z、组件级 stage timing、差异根因、当前 mainline 上的确认运行。
上海 L20X（140.40 GiB）要套用该布局，需先把 Qwen 移到独立进程并使用 weights-free
AdaLN，否则 DiT 峰值超出单卡容量。证据：`/cpfs/world-model/sglang/decoder-split/20261021-gpu-r6`
、`20261022-gpu-d2-th` 与 `20261022-gpu-smoke-ec4230cc7d`。

角色边界：部署方用 `--encoder-gpus`、`--denoiser-gpus` 与 `--decoder-gpus` 显式指定每个角色的物理卡，
均为调用方 `CUDA_VISIBLE_DEVICES` 中的**序号**（不是 `nvidia-smi` 编号），例如：

```bash
CUDA_VISIBLE_DEVICES=0,1,2 sglang serve --model-path MODEL_PATH \
  --num-gpus 2 --sp-degree 2 \
  --denoiser-gpus 0,1 --decoder-gpus 2
```

launcher 只做翻译与校验，不替用户分配：Denoiser 卡数必须等于 `--num-gpus`，角色之间不得共用同一张卡，
并且分卡只能在单节点上使用。Role 不配置时保持单角色同卡模式。编码、解码能力及各自的进程入口彼此独立；
会话协议不假设“一个角色一个进程”。共用 GPU 不等于合并进程，只有显式配置才会合并。
现已支持通过 CLI（`--encoder-gpus` / `--denoiser-gpus` / `--decoder-gpus`）或 `launch_pool_disagg_server()` 统一声明与编排各角色卡位。

## 独立 Decoder 渐进交付

`SGLANG_ZING_REMOTE_DECODE_PROGRESSIVE=1` 将一个独立 Decoder dispatch 内的
RGB 输出拆为 Lynn 的合法单 latent 切片（通常为 `1,4,4,4,4`），每片完成转换和
D2H 后即可独立交付。默认 `0` 保留原有整批路径；所有 Decoder rank 必须一致。
每个 dispatch 的共享内存总字节预算和两个在途槽保持不变，内部每片沿用原有
ready/ACK/CANCEL 生命周期，所有片结束后才归还该 dispatch 的槽。
帧范围、source alignment、条件版本和 EOS 仍按原有契约检查。
源会话每完成一个 AR 输出块即归还此次 dispatch。cross_chunk 模式复用延期 final
提交：当前 RGB 先交付，下一 dispatch 将前块 final 与本块 source/step0 联合计算，
避免本块输出等待下一块的首步预测。待处理块和历史仍受原预算约束，两个 quantum
配置不变；主动取消释放待处理状态、KV 和未消费 RGB 引用。
已接受的 Encoder 尾部前缀在最后一个就绪 AR 块后收集，避免空 RPC，也避免第一块
输出等待下一段前缀交接。单卡独立 Decoder 在接收下一份 latent 前完成当前发布。

该模式不修改 DiT 的 `SOURCE_WORK_QUANTUM` 或 Lynn 本地路径的
`DECODE_WORK_QUANTUM`，也不自动缩短 `joint_wait_ms` 的预算。
2026-10-27 基于发布分支 `f2894cda2e` 的本地候选将渐进远端路径的输入等待目标
对齐到本次可执行的一个 AR 块：当前块输入齐备即可唤醒，已到齐的后续输入仍可预取，
非渐进的双块收集策略不变。worker 不再为填满 joint 队列而先阻塞收取下一片 Encoder；
当前 DiT 完成后先提交独立 Decoder，再收集已接受的尾部前缀，保留原有 credit 和
`more_work` 语义，不额外引入空 RPC。EOS 仍走最终一次解码回执，避免覆盖尾帧引用。

该候选仅完成本地 CPU 调度、帧边界及生命周期回归；**未部署，当前候选的 480/736
TTFF、E2E、FPS、TPOC、ICL、画质及 Encoder/DiT/Decoder 各项耗时与显存均未实测**。
不把既有日志中的 50 ms 合并等待和约 70 ms 前置交接直接相加作为收益，也不把下面

## 配置时先检查什么

1. **把 Qwen 移出 DiT rank。** 当前主线仍需显式选择
   `--zing-conditioning-mode remote` 并提供服务 URL、expected profile 和 client config。
   独立 Qwen 与 source Encoder 可共卡，但需要把两进程的整卡占用一起考虑。
   [PR #331](https://github.com/seedleap/sglang/pull/331) 的 remote 默认值修改尚未合入，
   不要因文档里的推荐而省略参数。
2. **准备匹配的离线 AdaLN 表。** 主线 #378 已默认 weights-free，部署前按
   [AdaLN 表契约](/docs/sglang-diffusion/zing/specs/ADALN_TABLE)准备目标设备、权重和完整
   schedule 对应的表，检查零 projection storage、零 miss/fallback。
   SP2 历史四分支模型 ready allocated 从 127.90 降到 95.58 GiB/rank，
   节省约 32.32 GiB；这是加载阶段的对照，不能再次从矩阵峰值里扣除，也不代表所有 checkpoint
   都省同样多。更换硬件、权重或采样计划需重建表；Hopper 的表不能直接复用泰国表。
3. **使用 Lynn，避免加载闲置的原生 Decoder。** 主线 #325 已自动跳过该闲置权重；
   旧 TAEH3 已删除，其历史显存只能作历史证据。参考图 VAE 等剩余模块不会因此自动外迁。
4. **先确定输入与 KV 容量，再开 Graph。** 核对实际宽高、window/sink、prefix 上限及
   pool size=1；prompt 切换按主线固定 5 latent 重建。减少 window 或步数会改变模型行为，
   不能作为等价显存优化。Graph 需要额外 reserved 显存；开启环境变量不等于实际 replay。
   通用 `--enable-cuda-graph` 与 Zing 模型专用 Graph 路径也不能混同。

## Ulysses 与 fixed KV 准备链路

以下开关用于同配置逐项 A/B，每个 SP rank 必须保持一致。它们进入 Graph cache key；
更换设置后使用新的服务进程并完成预热。SP 拷贝消除、history 有效行裁剪与跨 Graph
history 复用默认开启，显式设为 `0` 可关闭对应优化；Norm 融合保持默认关闭。

| 开关 | 默认值 | 行为与适用路径 |
| --- | --- | --- |
| `SGLANG_ZING_FUSED_CURRENT_ROPE_KV` | 沿用原门控 | 已有的 current Q/K RoPE 与 KV 写入融合；固定 KV 路径。显式设为 `0` 可测独立 RoPE 与写入的对照 |
| `SGLANG_ZING_SP_DESTINATION_MAJOR` | `1` | QKV 直接打包为 Ulysses 目标布局，接收结果直接作为 attention 输入；Zing batch-one 的 eager 与 fixed 路径 |
| `SGLANG_ZING_FUSED_QKNORM_ROPE_KV` | `0` | fixed 路径中将 QK Norm 移到 SP 后，与 current RoPE、KV 写入合为一个 kernel；BF16、head=128、rotary=96 |
| `SGLANG_ZING_HISTORY_ROPE_LIVE_ROWS` | `1` | fixed history RoPE 只读写有效历史行，跳过池内空余容量；Graph replay 刷新设备上的有效行数 |
| `SGLANG_ZING_HISTORY_ROPE_CROSS_GRAPH` | `1` | pooled fixed 路径跨 Graph 复用连续稳定的历史前缀（通常为 prefix/sink），仅重算剩余有效行；要求 chunk RoPE reuse 开启 |

Norm 顺序调整用于减少中间访存和 kernel 数量。history kernel 仍按池容量启动 grid，
空余行对应的 block 提前返回。跨 Graph 开关另用有界 grid 处理待重算区间，
区间起止行作为设备 metadata 刷新；raw K、有效坐标或物理映射变化时缩短复用范围。
复用状态在整次执行成功后发布，capture 只额外保护会被后续 forward 覆写的复用行。
生产 `Graph=0` 的通用 eager 路径不经过新增 Norm/KV 和 live-history 融合，需与 fixed
链路的 eager microbenchmark 分别解读。复现命令和组件测量范围见
[SP resident profiling](https://github.com/seedleap/sglang/blob/main/benchmark/zing_h3_causal/SP_RESIDENT_PROFILING.md#attention-preparation-ablation)。

## 后续 PR 如何维护

后续 Zing H3 变更统一同步维护本页的相关部署策略、API 行为、benchmark 指标与验证状态；
详细契约和操作说明通过链接引用，不只更新 benchmark 文档。

范围包括权重常驻、Qwen/Encoder/Decoder 布局、KV、attention、Graph、精度、编译与采样默认值。

## 分离式 Encoder/Decoder 池化（N:M:K）、通用 SP=k 与全组件运行时弹性扩缩容（2026-10-29）

### 当前状态：旧共享 API 多 DiT 入口停用（2026-11-03）

旧的“一个公共 HTTP/WS API 入口自动选择多个 DiT”启动及候选路由代码已注释保留，
不再作为部署入口。旧多组 `launch_pool_disagg_server()` 调用会明确报错；
单组启动、其他模型的通用 launcher，以及 Encoder／Decoder 共模型多 service 不属于本次停用范围。
新部署使用独立 worker service，由 Master 通过 HTTP 显式建立 Encoder → DiT → Decoder 通信组；
操作入口见 [Worker group 测试 Master](https://github.com/seedleap/sglang/blob/main/benchmark/zing_h3_causal/WORKER_GROUP_MASTER.md)。

停用前检查发现旧候选路由存在以下故障处理问题：

- **会话释放失败后，重试可能找错 DiT。** 公共 API 在发出释放请求前，就删除了“该会话属于哪个 DiT”的记录。
  例如会话实际运行在第二个 DiT，释放请求超时后，重试可能被路由到第一个 DiT。
  第一个 DiT 返回“没有释放会话”时，上层仍可能将此次 RPC 成功视为清理完成，导致原会话资源没有确认释放。
- **回包超时后，重试可能重复执行。** 请求已发送给第一个 DiT 后，即使只是响应超时，旧逻辑也可能把同一请求再发给第二个 DiT。
  第一个 DiT 可能已经开始处理，因此两个 DiT 都可能执行该请求，而会话归属只记录一个，后续清理也可能遗漏另一个。

上述问题位于旧公共 API 的候选调度与会话释放路径，不是新 worker `destroy_group` 的语义。
目前采取停用旧入口，而非声称已修复其重试算法；重新启用前，必须保证释放确认前保留会话归属、
禁止未经确认的跨 DiT 状态请求重放，并补充释放超时和发送后回包超时的故障回归。

## 4D Block-Sparse Attention（CosGate v2，2026-10-30 Draft，PR #493）

2026-10-30，基于 main `480b48c853`（PR 分支已同步至 `2242cc4fa7`，代码提交 `942b66992b`，配套算子库 `seedleap-kernels` PR [#10](https://github.com/seedleap/seedleap-kernels/pull/10) `c7e3d6d2e8`）：接入 4D 块稀疏注意力（`block_sparse_attention`）与余弦门控融合双 Query 路由器（`fused_dual_query_block_router`，默认关闭，由 `SGLANG_ZING_SPARSE_ATTN_MODE=dual_query_topk` 与 `SGLANG_ZING_SPARSE_BUDGET_SCALE=0.95|0.90` 显式开启）。每个 chunk 仅在 `source_t0` 执行单次池化路由，后续去噪步直接复用块索引：
- **零硬编码 5 段候选块与双流几何解耦**：按 `KIND_TEXT=0`、`KIND_REF_VIS=1`、`KIND_SINK=2`、`KIND_WIN_SRC=3`、`KIND_WIN_FIN=4` 标记物理 KV 池；`source` 流完全由干净 `Q_src` 独立驱动，去噪流对 `WIN_SRC`（`0.65 Q_src + 0.35 Q_act`）与 `WIN_FIN`（`0.20 Q_src + 0.80 Q_act`）按信噪比解耦融合；
- **StreamDiffusionV2 风格 `C^0` 平滑锚点虚拟驱逐**：仅对 `KIND_REF_VIS` 执行余弦门控校准以保留服装/NPC 特征；当 `KIND_SINK` 相对局部窗口余弦 Z-score 跌破阈值（`z_c < -0.35`）时按 `ev_sink = mu_w - (1.5 + 2.0 * d_sink) * std_w` 平滑压低路由分，消除 17s 走廊转弯首帧墙壁穿模，无需物理重写前缀 KV；
- **`ZingChunkGraphs` 共享内存池世代生命周期加固**：捕获期临时关闭 Python 循环 GC、移除 `.pin_memory()` 与运行期池内单图驱逐（`max_graphs=16`，超限时整池排空重置 `_pool=None`），并将 `prefix_separate` 与 `_sparse_mode_epoch` 解耦，消除超长会话与高频 prompt/reference 切换下的 `cudaStreamCaptureStatusInvalidated` 与池复用冲突。

### Encoder reuse after communication-group teardown (2026-11-09)

A fresh source owner resets the Encoder's committed-frame watermark, latent/EOS
cursors and source-preparation state, including when a completed DiT link has
already dropped its owner before group destruction. This prevents a subsequent
player's first chunk from inheriting the previous player's progress. CPU tests
cover both normal destruction and rollback; production sequential-player replay
and same-condition performance remain pending. No model, KV budget, sampling or
transport setting changes are required.
