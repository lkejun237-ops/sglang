## Managed Player 与 CLI 并行准备

官网使用 `create.manual` / `inference_control=manual`。经过受管入口验签并绑定
`expected_publication` 的启动请求，如果携带已校验的 v2 `initial_frame`，且现有
`WHITEBOX_MODEL_STARTUP_PREPARE=1`、`WHITEBOX_BOUND_COMPUTE=1` 已开启，可以提前准备模型条件。
不增加客户端字段、另一个 Slot 或模型工作队列；没有预置帧、非受管调用、v1 和成员
Prefill 仍沿用各自原路径。

`manual` 继续控制生成和显示。带 `intent=model` 的可信预置帧只允许在同一玩家父绑定上
准备一个有界候选，不会自动启用推理、不提前发布模型画面。原 CLI descriptor/publication
检查保留；候选计算可与 CLI 加载重叠，实际使用必须等真实 CLI 与用户的模型启用操作。

- `SourceInference` 拥有候选，复用 `PlayStartup` 的 prepare/attach 与失败清理；启动资产
  由原手动会话持有，候选取消不破坏其后续启动输入。
- World 提供第一组真实条件后，先验证参考资源，再比较 Prompt、seed、有序图片槽位、
  格式与内容。SDK 的 `reference-0` 等上传 ID 与 World 的 `<Picture 1>` 属于不同命名空间；
  仅在真实 World 条件入口按 H3 的参考图顺序映射槽位，不排序、不改字节，不改原准备请求和指纹。
  没有协商启动预热窗口时，匹配则等待并复用候选；不匹配则确认释放后走原 World 条件流程。
  不同条件不能为了复用而改写 World 的权威数据。
- 真正提交首段时才选取满足 World 生效边界的真实私有视角帧。v2 条件预览不替代视频
  frame zero，保留真实像素、时间戳与来源身份。World 的 segment/epoch 不变，已准备的
  model session/generation 与首段创建在同一次 journal CAS 中提交；不提前留下已关闭的代次。
- 受管普通世界没有 World 条件通道时，仍需显式 enable，再按冻结条件和真实 CLI 帧接续。
  已建立的 WS/RTC 就绪状态传给候选，生成仍遵循原 attachment 与 first-presented 约束。
- 用户退出、CLI 失败或超时关闭候选；显式 live-F0 Prefill 优先，先退役可选候选再计算。
  模型失败不是缓存 miss，清理未知不允许继续借用 compute。取消/失败只作用于该玩家，
  不暂停共享 World，也不重启其他模型。
- 如果模型席位不足或当前尺寸缺少模型路由，且 Room 确认预热未取得席位，白模照常启动，
  游戏输入和 Harness 回执随白模可用。用户手动开启推理时才重新申请席位，按该次请求
  返回模型可用性。已取得席位或释放状态不明时仍由原绑定完成清理。

预置条件与实际 World 条件不同会退回原路径，因此不能仅凭请求带图就承诺启动提速。
复用条件、准入等待、CLI 时间、prepared 到实际 attach/首帧的时间应分别观察；准备成功
不表示浏览器已显示模型画面。CPU 合同验证不替代真实 480/736 GPU 的 TTFF、画质和峰值内存。

阅读顺序：`SourceSession._open_engine` → `SourceInference.prepare_startup` →
World 条件核对 → `adopt_preparation` → `RenderJournal.model_condition/start` →
原 `RenderSegment` prepare/attach。协议回归入口为 `test_whitebox_parallel_startup.py`；
部署状态和性能记录按具体发布回执维护，下文历史记录不代表本候选已上线。

### 与后续条件预热协作

通用 `WHITEBOX_PREFILL_ENABLED=1` 不代表 World 启动预热计划已开启。Room 还需要
`WHITEBOX_MODEL_CONTEXT_PREWARM=1`、对应的 CLI descriptor 和订阅能力，以及原玩家模型绑定。
普通并行准备只计算开场条件，不能据此跳过包含未来 Prompt/参考图的预热计划。

旧客户端的自动 `source_operation=create` 不发送 `inference_control=manual`。
对已声明 World 条件通道、已经启用推理的这类请求，Room 在首次订阅前也创建同一预热窗口；
普通非 World 源保持原路径。窗口等待真实通道绑定后再读取协商能力，不因订阅与首条件到达竞态跳过计划。

支持启动窗口时先协商计划，不等待可选并行准备完成：没有候选的计划或无响应到期保留原准备，
正式提交时仍核对实际条件；存在有效预热候选时，`ControlPrefill` 先确认可选准备子任务释放，
再在原父绑定上串行计算。不会申请第二个 Slot，也不会并行占用两个模型子任务。
清理无法确认时把失败保留到预热 owner，阻止后续候选和生成继续借用该子资源。

场景事务的 `require_matching_condition` 准备绑定特定快照和发布回执，继续保持原路径，
不能为了启动预热将其退役。共享世界仍使用每玩家私有视角，不暂停其他玩家的世界时钟。

当前代码候选的回归覆盖计划协商、空计划复用、原生子任务串行释放及未知清理保护。
真实 GPU、切换耗时、持续帧率和浏览器验收结果需按测试发布分别登记，不能由 CPU 合同推定。

未整体移植该提交的性能或训练改动。

- V2 S0 是原生尺寸的条件预览，不要求等于 source video 尺寸或真实首帧像素。
  PNG 编码上限仍为 2 MiB，正整数宽高乘积不超过 16,777,216，解码前检查 IHDR，
  保留原有不透明 8-bit RGB 与双 hash 验证。Room 不做 resize。
- V2 fingerprint 使用 `condition-preview-rgb24-v2`，包含预览宽高和原 prompt、
  seed、参考图、source stream、worker profile。`source.prepare` 显式携带

  首帧不同不会重新占租约。原 SourceSession 固定的 CLI 首帧 hash 约束模型 frame zero。
- Adapter 到原 worker 的内部 prepare/attach 命令携带 v2 版本；省略该内部字段的
  既有调用保持 v1。V1 fingerprint、等尺寸/像素检查和显式一次回退不变。
  重复 prepare 的版本、尺寸、像素均不可变化，prepare/attach 不推进 source 或 RNG。

本候选只验证原 owner 的 CPU 契约及真实 Torch tensor/packing，模型计算使用测试 peer。
未部署，未证明当前 GPU 进程源码、原生 ICE 或性能；480/736 的 Encoder/DiT/Decoder
耗时、显存及完整 TTFF/E2E/FPS/TPOC/ICL 需独立同条件验收。

## 两条启动路径

| 请求 | 条件准备 | 实际模型视频输入 |
| --- | --- | --- |
| 提供 S0 | CLI 启动与 S0 条件准备并行 | 等 CLI 就绪，以固定的真实 CLI 帧开始，再选最新帧 |
| 省略 S0 | 等 CLI 第一张真实视角帧，以它准备条件 | 仍使用同一张真实 CLI 帧开流，再选最新帧 |

外部 S0 只作为 `<Video 1>` / `origin=source_s0` 的 Qwen 条件预览，既不是普通
reference，也不是 source VAE 的第一张视频帧。S0 为 960×540、source/output 为
832×480 是合法组合。Room 保留 S0 原尺寸，模型复用现有 source-presentation
选桶和 resize；无需增加 Room 或前端的缩放策略。

`model.prepared` 表示条件与会话状态已准备，不表示视频出帧。仍需等 CLI 真实帧、
RTC 就绪以及同 preparation 的 attach；实际模型帧才计入 TTFF 和输出统计。
prepare/attach 不推进 source、latent、AR 或 RNG 游标，也不写 source VAE 历史。

## S0 编码与尺寸

继续使用可选 `startup.initial_frame`，描述其真实 `width`、`height`：

```json
{
  "protocol": "whitebox-startup-prepare-v2",
  "request_id": "request-123",
  "intent": "model",
  "initial_frame": {
    "format": "png",
    "width": 960,
    "height": 540,
    "encoded_size": 12345,
    "encoded_sha256": "<sha256 of PNG bytes>",
    "rgb_sha256": "<sha256 of decoded native RGB24>"
  },
  "initial_render": {"prompt": "...", "seed": 42, "references": []}
}
```

PNG 仍要求8位RGB或不透明RGBA、单帧、无ICC/EXIF声明；编码体不超过2 MiB，
解码像素数不超过16,777,216。宽高必须为正整数，文件实际尺寸须与声明一致，
文件SHA和原尺寸RGB SHA必须匹配。PNG头尺寸在分配像素内存前检查。
解码后的RGB最多48 MiB，适配层仍服从协商的消息和内存预算。

前端预取首帧，点击时已加载且合法就传；缺图、超限、加载失败或尚未完成则省略。
前端只放开固定832×480限制，沿用原尺寸Canvas读取RGB，不改变图像比例。
`initial_state_id`仍不支持；可选`world_revision`仍与实际CLI世界发布身份核对。
v2不接受已移除的`fallback_policy`字段。

## 准备失败的诊断合同

Room 在已建立的模型连接上执行 `init`、`source.prepare` 或 `source.attach` 收到错误、异常应答、断连或
无法解码的响应时，返回 `MODEL_PREPARATION_FAILED`、`stage=model` 和当前 `trace_id`。
合法的下游错误码保留在可选 `upstream_code`（仅限 96 字符 ASCII 标识符）；不把模型端的
`INVALID_COMMAND` 当成玩家/白模输入错误。旧的 `INITIALIZATION_FAILED` 也明确归为模型初始化。

公开 `content` 使用固定英文说明；原始异常正文、路径和输入不向浏览器透传。
Room 服务日志记录 trace、prepare/attach 操作、下游码及有界错误正文，不记录整条帧/参考图消息。
下游没有提供原因时，公开提示明确保留原因未知；不能从空闲 slot 推断准备成功，亦不能由此
断言作品损坏。容量、CLI 启动、身份冲突及连接错误继续保留其原有代码和阶段。

WTP 对接使用原 WS/RTC 可靠控制消息显示上述字段，无额外重试或资源申请。
此诊断改动不修复模型准备本身；CPU 协议回归通过不代表线上 GPU 推理已验收。

普通分段和连续模型会话也保留模型 `init` 与运行时错误的来源：初始化拒绝使用
`MODEL_PREPARATION_FAILED`，渲染中的错误使用 `MODEL_FAILED`，阶段均为 `model`。
下游错误正文只写有界服务日志；浏览器仅接收固定说明、合法 `upstream_code` 和 trace。
分段终态的 `segment.error_code` 与原始 `render.start` / `render.replace` 的
`operation.result.code` 保持一致，同时保留 `stage`、`trace_id` 和可选 `upstream_code`。

资源清理失败不能覆盖已知主错误。主错误继续传播，额外记录
`cleanup_code=RELEASE_UNKNOWN` 与实际 `resource_state`；没有主错误时，清理失败仍按
`RELEASE_UNKNOWN` 报告。取消仍保持取消语义。容量错误的阶段为 `admission`；分段录像准备、
编码器准备分别使用 `ARCHIVE_FAILED/archive`、`VIDEO_ENCODING_FAILED/encoding`。
尚未明确归因的输出处理错误使用 `RENDER_OUTPUT_FAILED/rendering`，不推断为模型故障。
控制执行中的服务端错误使用 `CONTROL_SERVICE_FAILED/control`，不改写成玩家输入错误。

CPU 回归入口为 `test_whitebox_error_origins.py`，并覆盖现有 interactive、startup、render
lifecycle 和 control queue 消费链。此范围没有穷举所有运行时、CLI、存储和浏览器失败；
未知原因仍按对应边界报告，不能由错误类别推断具体 GPU 或作品根因。

## 模型池容量范围

Gateway 的 `/v1/slots` 使用自身固定的 `model_revision` 与 `vae_fingerprint` 查询
Coordinator，避免把其他模型或不兼容 VAE 的空闲槽位显示为当前模型可用容量。
Coordinator `/v1/capacity` 的两个同名查询参数必须同时提供且非空；不带参数时仍返回
运维使用的全局池快照。模型别名、local decode 约束和可用 worker 判断复用 admission
的现有实现，不创建新的调度或租约策略。

模型范围内的有效预留租约、未确认释放和隔离状态不会因尚未出帧而算作空闲。
`waiting_sessions` 仍是共享等待队列的全局计数，当前队列记录没有模型范围身份；
其余 worker 负载按所选池聚合。此查询不是个人额度或白模 Room 准入承诺。
对应 CPU 回归位于现有 Coordinator、Coordinator HTTP 和 Gateway HTTP 测试文件。

## GPU prepare/attach

S0的宽高与`source_stream.width/height`独立。适配层和模型执行层校验
`len(rgb) == width * height * 3`，按S0尺寸创建条件Tensor，保持source ledger和
目标输出几何不变。条件fingerprint同时包含S0字节哈希、S0宽高、prompt、seed、
有序reference、source配置和模型profile摘要。

保留以下保护：

- prepare/attach 的 preparation/session/source/worker epoch 身份一致。
- 同一准备请求重试必须保留原S0字节、尺寸和条件，不得偷偷换图。
- attach完成前不能append；消息大小、内存账本和源帧顺序仍按原规则检查。
- 实际视频第0帧必须是Room固定的真实CLI帧；此校验比较CLI帧哈希，而非外部S0。
- 取消、断连、超时、释放未知和下一会话继续由现有生命周期处理。

取消Room、适配层、模型执行层对“S0必须等于CLI首帧”的比较，且首次append不得覆盖
已准备的S0。像素不同不会释放租约或重做准备；每次启动只取得一个模型租约。
无S0时使用CLI帧的条件准备仍是合法的串行路径。

## 帧与记录

Room继续固定一张真实CLI帧Fk；CLI捕获、预览、共享世界继续运行。模型准备完成后
发送Fk一次，再选择最新帧。Fk到下一帧的真实时间间隔保留，不伪造tick零、不改写PTS。
外部S0不插入视频，不占源帧编号，不冒充CLI来源。

startup receipt增加`condition_preview`（origin、width、height、rgb_sha256）和
`cli_frame_rgb_sha256`，分别记录条件图与真正的视频起点。原source/worker身份、
CLI proof、起始帧证据和配对归档继续保留。
