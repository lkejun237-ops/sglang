# SGLang PR Review

## 审查边界与输入

先读取目标仓库的 AGENTS.md、贡献指南及相关目录规则，确认 PR/base/head 或工作区 diff、需求与验收标准、设计文档、实际测试结果。区分新增问题与既有问题；缺少关键输入时先查看可得证据，指出仍无法判断的部分。审查默认只读，不顺带修复、发评论、申请算力、提交云作业或 merge；这些动作遵循用户的具体授权。

稍复杂的功能需要设计说明，回答：用户如何使用；有哪些决策与替代方案、为什么这样选；什么测试能证明正确性与性能。缺少设计材料时说明哪个关键问题无法判断，避免只因格式缺失就给代码判定失败。简单改动不用补整套文档。

## 以证据审查

- 过度设计：抽象、配置、通用性是否由真实需求支持，是否有更小且满足验收条件的实现。
- Legacy：明确仍需支持的调用者、数据或协议；质疑无使用证据的兼容分支，但不能未经授权删除兼容性。
- 正确性与测试：沿真实调用链检查正常、边界、失败、取消和资源释放；寻找实现会失败而现有测试仍通过的具体反例。按影响范围运行可用验证，记录命令与结果，不把未执行测试写成通过。
- 理解成本：职责混杂、重复逻辑、隐式状态、过长调用链和代码坏味道是否使理解更困难；只提出能解释实际成本的改进，不为偏好要求重写。
- 性能：比较条件、测量方法、硬件与样本是否一致，结论是否越过证据。没有性能数据就列为未验证，不能凭感觉报回归。

用户要求独立审查时，使用全新上下文的审查 agent，只提供需求、diff、必要上下文与原始测试证据，避免提供预设结论。工具不支持独立上下文时明确说明限制。审查 skill 不自动启用 dev-mode，不自动启动修复博弈或人类验收关卡。

## 输出与交付

先给可操作发现，每条包括严重度、精确位置、触发条件、影响、证据或复现及最小修复建议。明确区分已证实缺陷、待确认风险与非阻塞建议；不要为凑数编造问题。随后说明结论、实际验证和未验证范围，无阻塞发现不代表完整质量保证。

给 reviewer 阅读指引：用户可观察的变化、关键设计取舍、建议阅读的文件/类/方法顺序、重点审查路径及测试入口。复杂 PR 可附独立设计文档，简单 PR 在描述中说明即可。用自然语言解释行为与理由，保留必要技术名词，避免直接粘贴冗长 agent 日志；需要润色时采用独立编辑视角，不能把润色当成事实核验。

团队交付约定：找 bot review 时 cc 生栋，由生栋 review 并点 merge。记录待办即可；未经用户授权不发送通知，不猜测 GitHub handle，不自行 merge。

## SGLang 专用审查

先识别改动属于 serving runtime、模型适配、diffusion、kernel、benchmark 还是部署集成；只检查实际受影响的路径。

- 社区惯例：对照当前贡献指南、邻近实现、注册与配置约定、已有测试和 CI。需要判断上游可接受性时核验当前上游代码/文档或相关 PR，列出具体来源；本地派生仓库惯例不自动等于社区最佳实践。
- 上游合并：指出通用机制和内部业务逻辑的边界、额外依赖、API/默认行为变化、向后兼容及维护成本；用 reviewer 可能提出的具体问题说明风险，不承诺社区会合并。
- 运行时：输入形状、dtype/device、缓存状态、批处理和调度假设，取消/断连/EOS/异常后的资源释放，分布式 rank 控制流与 collective 次序；避免只检查单卡正常路径。
- 模型适配与优化：对照明确基准和冻结输入区分数值、生成效果、性能及功能支持。GPU 未执行时不能宣称精度或速度通过；无声视频不能代表音视频能力已验收。
- 性能证据：核对预热、编译开销、测量边界、硬件显存与算力、并行配置、输入规模及同步方式，区分组件诊断与真实端到端收益。

部署与模型业务约束以当前 AGENTS.md、资产契约和硬件 profile 为准，不在此硬编码会变化的默认 case、分块或设备参数。单活跃会话约束下仍检查 session/generation 身份与下一会话可用性，不增加没有需求的多会话调度。

若 ai-infra-pr-review 在环境中可用且改动涉及云脚本或资源操作，读取其基础设施风险部分补充审查；没有安装时直接按目标仓库的操作契约审查，本技能可独立使用。
