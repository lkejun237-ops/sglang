## 磁盘问题及构建方式

原 Room 镜像约 8.06 GB。旧构建曾将完整 SDK 放入基础层，后续删除后又 COPY 新 SDK；删除不会回收下层镜像数据，历史构建和容器引用继续保留这些层。

本轮使用仓库内 `docker/whitebox-browser-dependencies.Dockerfile` 生成不含业务源码及 SDK 的依赖根文件系统，再从冻结提交完整构建服务。不是在旧业务镜像覆盖文件。纯 Python、Node、Go 和浏览器依赖复用经校验的国内镜像；pip/npm/Go 依赖也使用国内源。

- CPU 镜像要求 SDK COPY 为 0；Room 为 1；业务源码完整 COPY 为 1。原生 `.so` 文件的单文件复制不应被误判为第二次完整源码复制，见 #560。
- 构建工作目录和 BuildKit 缓存放在独立数据盘；使用独立、受限的构建器。缓存保留是为了后续复用，不能无限写入根盘。
- 本轮完整镜像测试通过；另以普通运行用户逐文件校验 CPU 4,925 个文件、Room 11,400 个运行及 SDK 文件的内容。
- 已按范围清理 8 个确认无容器引用且远端可恢复的历史镜像记录。共享层仍被引用，**不能把镜像记录数量换算为磁盘回收量**；这一步没有获得明显的净空间回收。
- 发布后根盘约 78% 使用，剩余约 25 GiB；数据盘约 58% 使用。数值是本次观测，不是容量承诺。

## Redis 不应随磁盘清理而清空

Redis AOF 约 1.9 MiB，不是磁盘占满原因。这里保存 Slot 所有权、隔离状态和已验证清理回执；停用持久化或清空库可能丢失这些状态。本轮保持 `appendonly yes`、`appendfsync everysec` 及原有 RDB 配置，不删除 AOF、业务缓存、录像或世界资产。

## 残留占用的后续修复方向

已确认直接失败点是启动取消后的 SDK 清理证据缺失；仍需复现究竟是尚未进入 join，还是 join 失败后的回执未被保留。新版有限重试只能处理暂时性失败，不能替代缺失的原始证据。

后续应覆盖三个明确边界：

1. 原所有者证明尚未分配 SDK 资源时，返回绑定请求/玩家/代次的 `not_created` 回执。
2. 分配已开始时保留原清理任务和回执，等待确定终态；响应丢失时幂等查回，不把“查不到成员”当成功。
3. 仅在 SDK 和模型原生清理均确认后归还 Slot；CUDA/进程异常继续隔离。回归包括立即取消、启动失败、回执丢失重试及下一玩家接续。

这些方向尚未因本轮正常短试玩而被证明修复，不能把人工清理写成代码根因已解决。
